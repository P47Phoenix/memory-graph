# ADR 0004: Client/server access over gRPC and Raft replication

**Status:** Accepted (by the user, 2026-09-28; decisions taken with the user the same day). Supersedes the transport and single-process parts of [ADR 0003](0003-data-model.md) decision Q5 (a local Unix socket, no replication) and closes its open Windows question (named pipes). Evidence: [daemon and locking spike](../spikes/daemon-and-locking.md). Epic amendment: stories 20-25 in the [epic](../epic-code-memory-graph.md).

## In plain words

Read this section first. It uses no special vocabulary. Words with a link are explained in the [glossary](../glossary.md).

1. Today memory-graph is one program that opens one database file, and only one program may hold that file at a time. The command line links the database code directly. ADR 0003 decided (Q5, 2026-09-20) that a long-running program, `memory-graph serve`, should own the file and answer the command line over a private connection on the same computer.
2. This ADR goes further. The user wants a real database: a **client** that talks to a **server** over the network using a fixed, versioned language (a wire protocol), servers that can be run as a **cluster** of several machines, data that can **always be read** even while one machine is down, and writes that are **safe on disk** before they are acknowledged. (The user's reference point is DotNext.Net.Cluster's Raft implementation; see Context.)
3. Picture a library with several branches. Every branch keeps a full copy of the catalogue, so you can read at any branch. When you add a book, the branch you walk into passes it to the chief librarian (the leader), who records it in a ledger and only says "done" once more than half the branches have written the same line in their own ledgers with the ink dry ([fsync](../glossary.md#fsync)). If the chief librarian is away, the branches elect a new one within a second or so. Nobody reads a book that has not been recorded, and a recorded book is never lost. A branch may show you a catalogue that is a few seconds behind the ledger unless you ask for the "linearizable" mode, which checks with the chief librarian first.
4. What is decided (details in the table below): the wire protocol is [gRPC](../glossary.md#grpc--protobuf) (a widely used remote-call standard, in pure Rust, no `protoc` tool needed); the server and client are new crates, the command line keeps working exactly as today when no server is named; replication uses [Raft](../glossary.md#raft-leader-follower-learner-log-snapshot-linearizable-read) through the `openraft` library; every node accepts writes and forwards them to the leader; every node serves reads from its own copy (except for the few seconds while it installs a snapshot after falling far behind), with an optional "linearizable" mode that guarantees you see every acknowledged write; the on-disk layout gains a data directory with the store file, the Raft log and one snapshot.
5. What it buys: the command line and future MCP host never fight over the file lock; several readers work while an index runs; the database survives the loss of a machine; a Docker Compose file or a Kubernetes StatefulSet runs it as three nodes.
6. What it costs: about 37 story points over six stages (stories 20-25), two new young libraries (`tonic` for gRPC and `openraft` for Raft, neither yet at version 1.0), one extra "tell the disk to finish writing" per write (the Raft log next to the store), a snapshot that is a copy of the whole database file, and a data directory instead of one file when running as a server. No encryption on the wire yet (a follow-up once a pure-Rust encryption library is available), and no login or passwords.
7. Nothing about the database file format changes. An embedded single-file database still opens as before, and a file that a server wrote can be reopened embedded. The one addition is a small Raft bookkeeping table inside the store file that the embedded path ignores; this ADR records that as an exception to our rule that any change to what is written on disk gets a new format number, because old programs ignore the table safely and it is only ever created by a server.
8. Delivery: this document first (docs only; the user accepted it on 2026-09-28), then code in six stages A to F, each its own PR with the usual reviews.

| D1 | How do client and server talk? | The wire format is a public commitment and must be versioned from day one. | **gRPC over TCP** with `tonic` + `prost` (pure Rust). The `.proto` files are the contract, package `memory_graph.v1`; the generated Rust code is checked in and regenerated by a pure-Rust compiler (`protox`), so no `protoc` binary is needed. | D3 | How does the command line choose between a file and a server? | Zero-setup single-terminal use must keep working. | `--db <file>` (embedded, as today) or `--server host:port` (env `MEMORY_GRAPH_SERVER`); both at once is an error; neither means `./graph.redb`. `--read local\|linearizable` picks the read mode. |
| D4 | Who owns the file, and what happens when it is busy? | Restates ADR 0003 Q5 for TCP. | `memory-graph serve` owns the file. A `LOCK` sidecar next to the store names the holder (pid, listen address). An embedded open of a busy file retries with jittered back-off for 5 s, then fails with a message that names `serve` and the holder. Windows uses the same TCP path (named pipes are not needed; question closed). |
| D5 | How is data replicated? | The user wants writes accepted anywhere and data safe when a machine dies. | **Raft** via `openraft` (pinned exact version). Client and Raft traffic share one port. A log entry carries the command and, for indexing, the raw source bytes of up to 8 MiB of files. Applying an entry is idempotent and exactly-once. |
| D6 | How does a node know who it is and which cluster it belongs to? | Accidental double bootstrap or a node from another cluster would silently fork the data. | A data directory with `node.json` (node id, cluster id, advertised address, versions). `--bootstrap` mints a cluster id; `--join` copies it from the peer. Both are idempotent on a directory that already belongs to the same cluster and refused (`WrongCluster`) on one from another. |
| D7 | When is a write "done", and what does a snapshot mean? | The durability promise is the point of the exercise. | A write is acknowledged only after the entry is fsynced in the Raft log on a majority and applied by the leader in one fsynced store transaction that also records the applied index. A snapshot is a consistent copy of the store file (one read transaction, like `vacuum --compact`). The Raft bookkeeping table in the store is a compatible addition (no schema bump; exception recorded). |
| D8 | What do reads and writes see during trouble? | "Always readable" was a requirement. | Every node serves `LOCAL` reads from its own copy at all times, even without a leader (the one gap is the seconds while a node installs a snapshot; the client then tries its next endpoint); they may lag and JSON output says so. `LINEARIZABLE` reads go through the leader's read barrier and see every acknowledged write. Any node accepts writes and forwards them to the leader; with no leader the client retries until its write deadline. |
| D9 | How do nodes come and go? | Membership changes are where clusters lose data. | DotNext's warm-up model: a new node joins as a learner, catches up, then is promoted to a voter (joint consensus). `--standby` is a learner forever (read replica). `remove` refuses the leader, refuses 3 to 2 voters without `--force`, and anything below quorum. |
| D10 | How do operators see what is happening? | A cluster with no instruments is not operable. | `tracing` logs (text or JSON), a Prometheus `/metrics` endpoint, the standard gRPC health service (`SERVING` once the store is open; `memory-graph.ready` once a leader is known), and `cluster status --json` with the same numbers. |

**What this means day to day:** `memory-graph index` and `memory-graph search` work as today with a file. Add `--server host:port` and the same commands talk to a running `memory-graph serve`. Run three `serve` processes and they form a cluster; the command line can point at any of them.

## Technical version

**Words used below** (each is in the [glossary](../glossary.md) or defined here): a [snapshot](../glossary.md#snapshot--snapshot-isolation) is a frozen view for a reader; a [transaction](../glossary.md#commit--transaction) groups changes that succeed or fail together; [fsync](../glossary.md#fsync) forces written bytes to stable storage; [Raft](../glossary.md#raft-leader-follower-learner-log-snapshot-linearizable-read) is a consensus algorithm in which a leader replicates a log of commands to followers and an entry is committed once a majority holds it; a **learner** receives the log but does not vote; **joint consensus** is Raft's safe way to change membership; a **read barrier** (ReadIndex) is the leader confirming it is still leader with a majority before answering a read; **gRPC** is a remote-procedure-call protocol over HTTP/2 with messages described in `.proto` files; **protobuf** is that message encoding.

## TL;DR (for engineers)

- Four new crates: `graph-proto` (contract and converters, no runtime), `graph-server` (tonic services plus the openraft node), `graph-client` (`RemoteStore: Store` with an owned tokio runtime behind a synchronous facade), `xtask` (proto codegen with `tonic-build` + `protox`, checked in, CI diffs it). The CLI stays synchronous. `graph-store` gets no network code: it gains a remote-prepared file variant, a `RAFT_SM` marker table with marked write variants, `export_snapshot` and `install_snapshot`.
- The replicated state machine is the store. A log entry is a prost `LogCommand { IndexChunk | IngestExtraction | Prune | Vacuum | Noop }`; `IndexChunk` carries raw source bytes cut at 8 MiB per entry. Every replica applies an entry as `prepare` per file plus one `index_prepared_marked` transaction that also writes `last_applied` and membership. Transaction boundaries are therefore identical on every replica; query-identical, not byte-identical, replicas are the goal, proven by `run_differential`.
- Durability: the Raft log is its own redb file with `Durability::Immediate`; append commits before openraft's `LogFlushed` callback; apply is one store transaction carrying the marker. Restart replays committed entries above the marker; apply is exactly-once; "applied but not logged" cannot happen.
- Reads: `LOCAL` on any node any time; `LINEARIZABLE` via `ensure_linearizable` on the leader. Writes: any node, forwarded to the leader, acknowledged after majority fsync and leader apply.
- Delivery in six stages (epic stories 20-25, 37 pts). Stage 0 is this document. Stage A is a single-node server and client (one-member Raft over a loopback network, so there is one code path); B replication; C membership and forwarding; D linearizable reads and crash tests; E observability and packaging; F hardening.

## Context

ADR 0003 Q5 (2026-09-20) chose an owning daemon reached through a local socket, with a `RemoteStore: Store` client, because redb holds an exclusive file lock and snapshot isolation is in-process only. The [daemon spike](../spikes/daemon-and-locking.md) measured the round trip (0.003 ms per empty request, about 4 µs/KB of answer, independent of database size) and the lock (held for a whole index run, 20 s per 2.5 M tokens; retry starves under load), and concluded "keep the daemon". Story 12a was recorded as decided, not built; its wire encoding and the Windows transport were left open. The epic listed "network server" and "distributed storage" as out of scope.

On 2026-09-28 the user asked for more than the daemon: a real client/server database, hostable as a cluster, always readable, with durable writes accepted on any node, modelled on DotNext.Net.Cluster's Raft (warm-up of learners, `ApplyReadBarrierAsync` for linearizable reads, a persistent write-ahead log next to the state machine). This ADR records how that is done without breaking the embedded product, the pure-Rust rule, the configuration-equivalence invariant, or the versioned file format.

Verified facts the design rests on (2026-09-28, from the code):
- `Store` and `StoreRead` are object-safe and `Send + Sync`; `Query`, `SymbolQuery`, `Hit`, `SymbolHit`, `RepoInfo`, `IngestStats` and `Node` are serde types; `StoreError`, `BatchFile`, `Extraction`, `IndexOptions` and `Page` are not; `PreparedFile` is not serializable and its fields are crate-private.
- `V2Store` uses redb's default `Durability::Immediate`: every commit fsyncs. `commit_each` with `chunk_bytes = usize::MAX` makes one `index_prepared` call one transaction.
- Node and term ids are sequential counters bumped inside the transaction, so replicas applying the same entries in the same order allocate identical ids.
- `compact` is already a consistent copy-every-table loop under one read transaction; `export_snapshot` is factored from it.
- The conformance case `snapshot_is_frozen` requires server-side snapshot handles; the harness calls `Harness.open` per case with that case's extractors (most pass none, `claimed_extension_extractor` passes its own), so a test server must be configurable per `open` call.
- No tokio, async or TLS exists in the workspace. `scripts/check-no-c-deps.py` fails on a `links` key or a build script using cc, cmake, bindgen, cxx-build, pkg-config or vcpkg. `.dockerignore` admits only `Cargo.*`, `crates/` and `examples/`.

## Decisions (technical detail)

### D1: transport and contract

- **gRPC** with `tonic` 0.14 (`transport`, `codegen`, `prost` features only; never `tls*`) and `prost` 0.14 (the current releases on 2026-09-28; the plan's earlier 0.12/0.13 figures were stale). Package `memory_graph.v1`; a breaking change bumps the package to `v2` and is served next to `v1` for one release. `PROTOCOL_VERSION = 1` is exchanged in `Hello` with binary, protocol and store format versions, the extractor version set hash, the node id and the known leader; an unknown protocol version is refused with `FAILED_PRECONDITION`. The client also sends its version as the `mg-protocol-version` metadata header on every call, and a server interceptor refuses a call whose header names another version with `FAILED_PRECONDITION` and a typed `Protocol` detail (a call without the header, from a generic gRPC tool, is let through). A detail-less `FAILED_PRECONDITION` (a proxy) is a refusal, not a protocol error, and a detail-less transport loss (`UNKNOWN`, `CANCELLED`, `DEADLINE_EXCEEDED`) is a lost connection, never a protocol error.
- **Code generation** runs in `xtask` (`cargo run -p xtask -- proto`) with `tonic-build` fed by `protox`, a pure-Rust protobuf compiler, so no `protoc` binary is needed on any machine. The generated code under `crates/graph-proto/src/gen/` is checked in; a CI job regenerates and fails on `git diff --exit-code`.
- **Services:** `Store` (`Hello`, every `StoreRead` method, `OpenSnapshot`/`CloseSnapshot`/`SnapshotStats`), `Write` (`Index` client-streaming, `IndexFile`, `IngestExtraction`, `Prune`, `Vacuum`), `Admin` (`Status`, `Members`, `Leader`, `AddLearner`, `Promote`, `Remove`, `TransferLeader`, `TriggerSnapshot`, `Compact`, `SysInfo`, `Metrics`), `Raft` (node to node: `AppendEntries`, `Vote`, `InstallSnapshot` client-streaming) and `grpc.health.v1`. `Descendants` and `FileTokens` are server-streamed in 4096-node batches. `Search` and `SearchSymbols` apply a default limit of 1000 and set `applied_default_limit`, so the client pages to completion when the caller asked for no limit; `RemoteStore` opens a snapshot handle for the duration of that paging (as `children_page` and `descendants_page` already require), so the pages come from one frozen view and cannot straddle an apply. Every read carries a `View { mode: LOCAL | LINEARIZABLE | snapshot_id }`.
- **Snapshot handles:** `OpenSnapshot` returns a server-side handle with a random 64-bit id; the table keeps at most 64 per connection (`INVALID_ARGUMENT`) and 1024 per server (`RESOURCE_EXHAUSTED`), expires a handle at the store's snapshot max age (15 min, ADR 0003 Q6; checked on every use), drops every handle a connection opened when that connection closes, and an idle reaper runs every 5 min. A handle is readable from any connection that knows its (unguessable) id, but its lifetime belongs to the opening connection: after a reconnect the client gets `SnapshotExpired` and opens a new one. This is what makes the conformance case `snapshot_is_frozen` pass remotely.
- **Error mapping:** `Rejected`, `NotUtf8`, `TooLarge`, `InvalidSpan`, `Schema` -> `INVALID_ARGUMENT`; `Locked` -> `UNAVAILABLE`; `SchemaMismatch`, `LegacyFormat`, `SnapshotExpired` and a protocol mismatch -> `FAILED_PRECONDITION`; `Corrupt` -> `DATA_LOSS`; `Storage` -> `INTERNAL` (disk full -> `RESOURCE_EXHAUSTED`); not-leader -> `UNAVAILABLE` with a `NotLeader { leader_id, leader_addr }` or `NoLeader { retry_after_ms }` detail. The typed `StoreError` rides in `Status.details` so `StoreError <-> Status` round-trips (property-tested).
- **No TLS** in this ADR: `rustls` needs a crypto provider and the pure-Rust ones (`ring` is C and assembly; `aws-lc` is C) would fail the gate. The gate gains a name deny-list (`ring`, `aws-lc-sys`, `openssl-sys`, `libz-sys`) so a failure names the culprit, and `scripts/test_gate.py` asserts `cargo tree -i ring` is empty. Deployments needing encryption terminate TLS in a sidecar or mesh until the trigger above fires.

### D2: `RemoteStore: Store` and the raw-bytes index path

- `graph-client::RemoteStore` implements `Store` over a tonic channel with an owned tokio runtime and a synchronous facade (`block_on`). Calling it from inside a tokio runtime panics with a message that says so (documented and unit-tested); the CLI has no runtime of its own.
- `prepare` on the remote store returns `PreparedFile::remote(bytes)` (a new `Prepared::Remote` variant in `graph-store`): the footprint is counted for the memory budget, `is_unchanged` is `false` (the server decides), and the embedded store **rejects** a remote-prepared file with `Rejected` (a conformance case). `index_prepared` streams one `Index` RPC per group commit: a header, then one `FileBytes` per file.
- Rationale for raw bytes over the alternatives: the `Extraction` is 10-20x larger than the source; shipping the prepared V2 form would tie the wire to `codec.rs`. The server parses with its own extractors; the extractor hash gate (D5) keeps replicas from diverging.
- `ClientConfig { endpoints, read_mode, retry { base 50 ms, cap 2 s, budget 5 s }, write_deadline 10 s }`. Retries with jitter on `UNAVAILABLE` (writes also on a lost connection); `NotLeader` switches the channel to the named leader, with jittered back-off from the second consecutive switch; a write that exhausts `write_deadline` on a retryable error fails with `NoLeader` (CLI exit code 4); index, prune and vacuum entries are idempotent, and so is `IngestExtraction` when the extraction is identical (which a retry of the same request is), so at-least-once delivery after a leader change is safe.

### D3: target selection in the CLI

- Global `--db <file>` becomes optional; `--server host:port` (env `MEMORY_GRAPH_SERVER`) selects the client. Both given is an explicit error (checked in code, because the env path bypasses clap's conflict check); neither means `./graph.redb` as today. `--read local|linearizable` (env `MEMORY_GRAPH_READ`, default `local`).
- With `--server`: `--chunk-bytes` is refused (the leader cuts log entries at 8 MiB, D5, and apply is always one transaction per entry) and `--cache-bytes` is refused with "pass to serve"; `--jobs` warns (parsing happens on the server); `--memory` still bounds bytes in flight on the client; the client-side disk guard is skipped and the server's guard returns a typed error. `sysinfo --server` prints the server's report under a `server <addr> node N (leader: M)` header. `vacuum --compact --server` is `Admin.Compact`. The progress board relabels parse as "send" and commit as "replicate: acked by leader N (idx K)"; `--stats` gains an `rpc` row.
- Exit codes: 3 for no leader on `cluster leader`, 4 for a write deadline that expired without a leader, 5 for a protocol or version mismatch.

### D4: `serve` ownership and the LOCK sidecar

- `memory-graph serve --db <file> --listen <addr>` owns the store exclusively (redb's lock) and writes `<file>.LOCK` (pid, listen address). An embedded open that hits `Locked` retries with jittered back-off for 5 s (ADR 0003 Q5), then fails with a message naming `serve` and, when the sidecar exists, the holder. Two `serve` on one file: the second fails with `Locked`.
- Windows uses the same TCP path; ADR 0003's open named-pipes question is closed.
- Graceful shutdown on SIGTERM (or `Ctrl-C` on Windows): stop accepting, finish in-flight applies (30 s grace), `Raft::shutdown`, close redb, remove the sidecar.

### D5: openraft, one port, log entry format, idempotent apply

- `openraft` pinned to an exact `0.9.x` (`=0.9.25` on 2026-09-28; 0.10 is still alpha) with features `serde`, `storage-v2`, `generic-snapshot-data`; isolated behind `graph-server/src/raft/{types,log_store,state_machine,network,node}.rs` so API churn stays in one place. Client and Raft services share the one listening port.
- **Log entry** = prost `LogCommand { IndexChunk | IngestExtraction | Prune | Vacuum | Noop }`. `IndexChunk { org, repo, reindex, files[{ path, bytes, language?, origin? }] }` is cut by the leader at `RAFT_ENTRY_MAX_BYTES = 8 MiB` (a single larger file is an entry of its own, the same rule as `--chunk-bytes`). `IngestExtraction` (caller-supplied `Extraction`, no bytes) is the one command that ships an extraction. `Prune` (not dry-run) and `Vacuum` are logged; `prune --dry-run`, all reads and `compact` are node-local (`Admin.Compact` takes the store's write slot, pauses apply, rebuilds and renames).
- **Apply** = `prepare` for each file, then one `index_prepared_marked` transaction (chunking forced to `usize::MAX`, whatever `serve` was started with; `serve` has no `--chunk-bytes`) that also writes `last_applied` and membership into `RAFT_SM`. So a crash can never leave part of an entry applied without the marker, and transaction boundaries never depend on a per-node setting (configuration equivalence). Exactly-once by construction: an entry at or below the marker is skipped but still answered (openraft requires one response per entry passed to `apply`). openraft learns the marker through `RaftStateMachine::applied_state`; the log store implements `save_committed`/`read_committed` so a restart knows which entries are committed and re-applies exactly those above the marker. A single-node server is a one-member Raft over a loopback network, so there is one code path and the cluster grows by `add-learner` without a restart.
- **Determinism guard:** the extractor version set hash rides in `Hello`, in openraft's `Node` metadata (checked at `AddLearner` and promotion) and in snapshot metadata. Byte-identical replicas are not a goal (redb page layout may differ); query-identical replicas are, and `run_differential` proves it.

### D6: data directory and identity

```
<data-dir>/            (Docker: /data)
  node.json            node_id, cluster_id, advertise, binary/protocol/format versions
  graph.redb           the V2Store (state machine) + RAFT_SM table {last_applied, membership}
  raft.redb            openraft log (index -> entry) + hard state (vote, committed, last_purged); Immediate durability
  snapshots/snap-<term>-<index>.redb (+ .meta: term, index, membership, sha256, size, extractors_hash); one kept
  LOCK                 pid + listen addr
```

- `--bootstrap` mints `cluster_id` and starts a one-member cluster; `--join <peer>` starts empty, copies the cluster id from the peer, is added as a learner and catches up; `--auto-promote` promotes once lag is zero; `--standby` stays a learner. Neither flag = restart from persisted state. Both are **idempotent** on a directory that already belongs to the same cluster (Compose and Kubernetes restart with the same command line) and refused with `WrongCluster` on one from another cluster. A non-empty store joining as a learner needs `--accept-snapshot-overwrite`. A double `--bootstrap` on two empty directories creates two clusters; the cluster id check and a loud warning are the mitigation.
- `--restore <snapshot.redb>` with `--bootstrap` seeds a new cluster (new cluster id on purpose) from a backup taken with `cluster snapshot --out`.

### D7: durability, snapshots, purge; the `RAFT_SM` exception

- **Guarantee:** a write is acknowledged only after (1) the entry is appended and fsynced in `raft.redb` on a majority (`RaftLogStorage::append` commits redb before invoking the `LogFlushed` callback) and (2) the leader has applied it in one fsynced store transaction carrying `last_applied`. On restart a node replays committed entries above the store's marker; "applied but not logged" cannot happen because apply only follows commit; apply is exactly-once because of the marker. `LOCAL` reads may lag; `LINEARIZABLE` reads see every acknowledged write. Two fsyncs per entry is the accepted cost; stage A and B measure it before any batching optimisation. A refused entry (a deterministic store refusal, the same on every replica) still moves the marker, alone, in its own transaction, so the marker always equals openraft's `last_applied`. **An error does not prove a write failed:** openraft applies entries in batches, and an I/O error on one entry fails the call, dropping the responses of the earlier entries of that batch, which did commit; the node stops and those clients see an error for a write that landed. Retrying is safe for the reason in D2 (every write command is idempotent on a retry of the same request), and the client treats such an error as retryable, not as proof the write was lost.
- **Snapshot** = `export_snapshot(dest)` (factored from `compact`: one read transaction, every table copied, so it is consistent), streamed in 1 MiB chunks, installed on a follower by closing the store, renaming and reopening under the slot's write lock. Log purge follows a snapshot per `--snapshot-log-entries`, `--snapshot-log-bytes` and `--log-keep-entries`; the disk guard counts `raft.redb` plus one snapshot copy.
- **Replication details settled in the stage B review (PR #114):**
  - *AppendEntries and openraft's timeout.* openraft 0.9.25 wraps every `append_entries` call in a hard timeout equal to `heartbeat_interval` and has no separate knob for it (only snapshots have `install_snapshot_timeout`). An entry of several MiB may not cross a slow link and be fsynced within a heartbeat, and cancelling the RPC would make it never arrive. So `GrpcNetwork` runs an `AppendEntries` that carries entries as its own task (bounded at 120 s); openraft's timeout only ends the wait, and its retry with the same vote, previous log id and first entry joins the transfer still under way (a retry asking for more entries, the log having grown meanwhile, is answered `PartialSuccess` up to the last entry the transfer carried). Any other request, and any request under another vote, aborts the running transfer before sending, and dropping the connection (openraft rebuilds replication on a membership or leader change) aborts it too, so at most one transfer per peer uses the link. Heartbeats go directly and keep the follower from electing. Multi-entry RPCs are capped at `RAFT_RPC_MAX_BYTES = 4 MiB` (`PayloadTooLarge` makes openraft send fewer); a single entry bigger than that (an 8 MiB chunk, or one larger file) is sent alone. A plain timeout keeps the channel; transport failures reconnect; every failure is logged per peer at most every 10 s and shown as `PeerLag.last_error` in `Status`.
  - *Log compaction after a purge.* redb never returns freed pages to the file system, so after a purge `raft.redb` is compacted in the background when the file is at least twice its live pages plus 1 MiB. `Database::compact` holds the log's write lock, so appends, `save_vote` and `save_committed` wait for it, and the Raft core awaits those. **Stall bound:** it runs only when the live log after the purge is at most 64 MiB (`COMPACT_MAX_LIVE`), which redb rewrites plus a few fsyncs in well under a second on a 100 MB/s disk, below the 1 s minimum election timeout; a larger live log is skipped and a later purge, with less left, tries again. Closing the log (the last handle dropped, or `RaftNode::shutdown`) waits for a running compaction, whose clone keeps the file open, so a restart in the same process never finds `raft.redb` locked.
  - *Disk.* A follower whose disk guard trips refuses an `AppendEntries` with entries (`RESOURCE_EXHAUSTED`) before appending, so it lags and catches up once space is freed while the others commit; heartbeats are still answered. An `InstallSnapshot` needs `--min-free-disk` plus two copies of the snapshot (the received file and the staged store; the store and the retained snapshot are separate files, so the copy is inherent), checked before receiving. A leader checks its disk before proposing; an I/O error while appending or applying anyway (disk full after the check included) stops that node, which restarts and replays from its marker (follow-up: #115).
  - *Identity at start.* `node.json` records `bootstrapped`; a node that minted its cluster initializes it on any start where the log is not initialized yet (a crash between writing `node.json` and initializing). The listener binds before anything is written, and a directory holding only what a failed first start leaves (an empty store, a blank log, no `node.json`) is started as empty. An initialized directory whose `raft.redb` is missing or blank while the store has applied entries is refused (the node would forget its vote and could vote twice in a term), as is one whose store is missing while the log has state.
  - *Cluster id and extractors on the wire.* Every Raft RPC carries `mg-cluster-id` and `mg-extractors-hash`; a node refuses (`FAILED_PRECONDITION`) another cluster, a missing cluster id once it has one, and other extractors. An uninitialized node adopts the cluster id from `AppendEntries`/`InstallSnapshot` only, never from a `Vote`. `AddLearner` first asks the target's `Admin.Status` and refuses another node id, another cluster or other extractors; its blocking wait for catch-up is ours (60 s, an error on timeout), since openraft's own gives up after half a second and reports success. `Promote` adds one voter (`ChangeMembers::AddVoterIds`), so concurrent promotes do not undo each other.
  - *Protocol version.* The `Raft` service's messages changed shape during stage B without a `PROTOCOL_VERSION` bump: stage A never sent them (a single node has no peers), so no deployed pair of nodes can disagree about them. From stage B on, a change to them bumps the version like any other message.
- **`RAFT_SM` exception to the version-bump rule:** the table is a compatible addition. It is created lazily by the server's first `index_prepared_marked` or `install_snapshot`, never by `V2Store::open`, so an embedded file reopened embedded stays byte-identical (the existing reopen property) and never gains the table. Embedded readers guard `TableDoesNotExist` the way `describe` already does for `OPEN_BATCH`; an older binary opens a served file, never asks for the table and ignores it (redb tables are named and opened on demand). A newer binary treats a missing marker as "never replicated" **only** for `--bootstrap` or `--join` on an empty store; a `serve` restart on a non-empty store with no marker is refused with an error naming `--accept-snapshot-overwrite`, because the marker may have been dropped rather than never written (next point). The new `compact`/`export_snapshot` copy it like any other table, but the current `compact` is a hand-maintained table list, so an **older binary's `vacuum --compact` on a served file silently drops `RAFT_SM`**; that is why the restart refusal exists (without it a node could re-apply from the log start or trip openraft on `applied < last_purged`). Golden-byte tests cover the marker encoding. This is recorded here so the invariant in `CLAUDE.md` stays honest: every other stored-byte change still bumps `V2_SCHEMA_VERSION`.
- **Note (retries after a lost connection):** a write retried after its connection was lost reports what the retry did, not the sum. A `prune` that landed before the connection dropped reports 0 removed on the retry (the files are already gone); the stored state is correct, only the count on the client is not the first attempt's. The same holds for `vacuum`.

### D8: read modes and write forwarding

- `LOCAL`: served from the node's own store at all times, including during elections and partitions, with one exception: while a follower installs a snapshot (D7: close, rename, reopen) its reads fail with `UNAVAILABLE` and the client moves to its next endpoint; server-side snapshot handles open on that node end with `SnapshotExpired`. JSON output carries `stale_possible: true` when the node has no known leader or lags the leader's committed index.
- `LINEARIZABLE`: the request goes to the leader, which runs `ensure_linearizable` (openraft's ReadIndex barrier, the analogue of DotNext's `ApplyReadBarrierAsync`), waits for its applied index to reach the read index, then serves. On a minority partition this fails with `NoLeader`.
- Writes on a non-leader are forwarded server-side; the response carries `forwarded_to_leader`. With no leader the server answers `NoLeader { retry_after_ms }` and the client retries until `--write-deadline`; `index` shows "waiting for leader" on the board.

### D9: membership lifecycle and guards

- `cluster add-learner`, `promote`, `remove`, `members`, `leader`, `transfer-leader`, `status`, `snapshot` talk to `Admin` on any node (forwarded to the leader where needed).
- `remove` refuses the leader (transfer first), refuses reducing 3 voters to 2 without `--force`, and refuses anything that would drop below quorum. Promotion uses joint consensus; promotion of a node whose extractor hash differs is refused.
- **Settled in stage C (epic story 22):**
  - *Join.* `serve --join <peer>` on an empty directory starts as an uninitialized member, serves, then sends `Admin.Join { node_id, advertise, extractors_hash, store_format_version, protocol_version, auto_promote }` to the peer, which forwards it to the leader; the joiner retries (back-off to 2 s) while no leader answers, up to `--join-timeout` (default 2 min), and fails at once on a refusal. The leader refuses other extractors, store format or protocol, a node id that is a member at another address, and a node id that is already a voter (an empty directory under a voter's id lost its vote and log), asks the joiner who it is (`Status`: node id, cluster, extractors), adds it as a learner and answers the cluster id, which the joiner adopts and writes to `node.json` (it may already have adopted it from the first `AppendEntries`; a mismatch is `WrongCluster`). The `listening on` line is printed after the join.
  - *Idempotency and `WrongCluster`.* `--bootstrap` or `--join` on an initialized directory is a restart. For `--join` the peer is first asked its cluster id (5 s); another cluster is refused with `StoreError::WrongCluster { expected, found }` (typed detail, `FAILED_PRECONDITION`, CLI exit code 6) before any file is opened; an unreachable peer is only warned about, so a whole cluster can restart at once. `AddLearner` and `Promote` report a node of another cluster with the same typed error. A directory holding a store or a log but no `node.json` is refused for `--join` unless `--accept-snapshot-overwrite`, which moves what it holds into `replaced-<secs>/` (nothing is deleted) and joins empty; a directory holding only what a failed first start leaves is started as empty, as for `--bootstrap`.
  - *Auto-promote.* The promotion runs on the leader, a task per node id started by `Join { auto_promote: true }`: once the joiner's matched index equals the leader's last log index it promotes through the same guarded path as `cluster promote` (`AddVoterIds`, joint consensus), retrying a refused change, for up to an hour. The intent is not persisted in the log: the joiner re-sends `Join` every 2 s while it is a learner (to the leader it knows, else its peer), so a restart of the joiner or a change of leader re-arms it. `--standby` (the default without `--auto-promote`) never asks. The hidden stage B flag `--wait-for-membership` is retired; `InitMode::Uninitialized` stays for the library and the test bed (a node that waits for `cluster add-learner`).
  - *Guards.* `Promote` asks the target's `Status` again at promotion time (so a learner restarted with other extractors is caught) and refuses an unknown id or a voter. `Remove` refuses the leader; refuses, whatever `--force`, a removal after which the voters that are reachable now (the leader, plus peers whose RPCs succeed and that have matched something) would be fewer than a quorum of the remaining voters, or no voter would remain; and refuses 3 voters to 2 without `--force`. A learner is removed without quorum checks. `RemoveVoters` with `retain = false` removes the node entirely.
  - *Transfer.* openraft 0.9.25 has no leadership transfer, and `Raft::trigger().elect()` alone cannot move leadership: the voters reject a vote request while their leader lease (`election_timeout_max` since the last heartbeat or append) holds, and openraft ignores the trigger on a leader. So `TransferLeader` on the leader checks the target is a voter whose matched index equals the leader's last log index (waiting up to 10 s), then switches its own heartbeats and elections off (`runtime_config()`) and answers new writes and read barriers `NoLeader` (clients retry, as in an election), so nothing renews the lease; waits the lease out; and sends `Admin.TriggerElect` to the target, which calls `trigger().elect()` with a term above every candidate's, repeating every two leases until the target leads or 20 s pass. Heartbeats, elections and writes are switched back on whatever the outcome (a guard); if another node wins, the transfer reports it.
  - *Forwarding (D8).* A write on a node that is not the leader is forwarded over the ordinary `Write` service, from inside the handler (async, one cached channel per leader address); `Index` streams through a 2-message channel (bounded memory), and a client stream that fails mid-way cancels the forwarded call rather than ending it cleanly. The answer is the leader's with `forwarded_to_leader` set, and `Admin.Status.writes_forwarded_total` counts forwards (stage E exports it). A forwarded request carries `mg-forwarded-by`; a node never forwards such a request again (a non-leader answers `NotLeader`, and the client goes to the leader itself), so there are no loops. No known leader, or a forward that cannot reach it (transport failure), answers `NoLeader { retry_after_ms }`; any answer from the leader is passed through. Membership commands are forwarded the same way over `Admin`. A `LINEARIZABLE` read on a non-leader asks the leader for its read index (`Admin.ReadIndex`: the leader's `ensure_linearizable`) and serves once its own applied index reaches it (10 s bound, else `NoLeader`): the read sees every write acknowledged before it began without moving the data. Stage D tightens this and adds its crash tests. The test fault plan also gates forwarding, so a partitioned node cannot reach the leader by the back door. The client's write deadline still bounds retries, not a call already in flight (#116): a forward to a leader that cannot commit waits like a direct write would.

### D10: observability

- `tracing` with `--log-format text|json` and `--log-level`. `--metrics-listen` serves Prometheus text on hyper: `mg_raft_term`, `mg_raft_leader_id`, `mg_raft_role`, log/committed/applied/snapshot indexes, `mg_raft_replication_lag{peer}`, `mg_store_bytes`, `mg_log_bytes`, `mg_rpc_duration_seconds{rpc,outcome}`, `mg_writes_forwarded_total`. The same numbers appear in `cluster status --json`.
- `grpc.health.v1`: `SERVING` once the store is open; service name `memory-graph.ready` requires a known leader. `memory-graph health [--ready] --server` is the probe for shell-less images (the Docker `HEALTHCHECK` uses it).
- Packaging: `Dockerfile` gains `EXPOSE 7000` and the health check; `deploy/compose/cluster.yml` runs three nodes (node1 `--bootstrap`, node2/3 `--join node1:7000 --auto-promote`) with health-gated `depends_on`; `docs/deploy/kubernetes.md` describes a StatefulSet with a headless service for `--advertise`, the node id from the ordinal, gRPC readiness on `memory-graph.ready`, a PodDisruptionBudget of `minAvailable: 2`, and `cluster remove` before scale-down.

## Alternatives considered

| Alternative | Why not |
|---|---|
| Unix socket + length-prefixed JSON (ADR 0003 Q5 as written) | Local only, so no cluster; no Windows story without named pipes; JSON has no schema versioning of its own. The spike's numbers still justify the daemon; only the transport changes. |
| HTTP/1.1 + JSON | Simple, but streaming (`Index`, `Descendants`, `InstallSnapshot`) needs chunked framing and a custom schema story; gRPC gives both plus generated clients in other languages. |
| Custom binary framing over TCP | Smallest dependency set, but a bespoke protocol needs its own versioning, tooling and clients; gRPC's cost is one runtime (tokio) that Raft needs anyway. |
| `raft-rs` (TiKV) | Provides the core algorithm only: log storage, transport, snapshots and membership orchestration are all left to the user, which is most of the work. `openraft` ships them with async traits that fit tonic. |
| Primary plus copies (log shipping, no consensus) | Cannot accept writes on any node, cannot fail over safely without an external coordinator, and "durable" would mean "on the primary's disk". |
| Leader leases instead of ReadIndex for linearizable reads | Faster reads but depend on clock bounds; ReadIndex costs one heartbeat round and has no clock assumption. Open question Q5. |
| Ship the `Extraction` or the prepared V2 form in the log | 10-20x larger than the source, or couples the wire to `codec.rs`. Raw bytes plus a deterministic apply is smaller and keeps the codec private. |
| Per-node fsync only on the leader | Loses the "majority has it on disk" guarantee that the user asked for. |

## Consequences

**Positive**
- Readers no longer fight the index run for the file lock; a future MCP host (still out of scope; epic open question 5, issue #109) becomes a client of `serve` or lives inside it.
- The database survives a node loss; writes are durable across a majority; reads stay available on every node.
- One code path from a single embedded file to a three-node cluster: a single-node `serve` is a one-member Raft, and `add-learner` grows it in place.
- The contract is explicit (`.proto`, `protocol_version`), and generated clients in other languages come for free.

**Negative / risks**
- Two new pre-1.0 ecosystems (`openraft`, and `tonic`'s pace): pinned exactly, isolated behind `graph-server/src/raft/` and `graph-proto`.
- Two fsyncs per write and a Raft log that grows until a snapshot; measured in stages A and B, bounded by the disk guard.
- A snapshot is a copy of the whole store file; install time on a large store is a revisit trigger.
- Mixed extractor versions across replicas would diverge them; the promote-time hash gate refuses that.
- `block_on` inside a runtime panics; documented and tested. Windows has no SIGTERM (the kill test uses `TerminateProcess`) and its open-file sharing rules complicate the rename-on-install path; stage B tests it.
- No TLS and no auth: only for trusted networks until the follow-ups land.
- The `RAFT_SM` table is an exception to "every stored-byte change bumps the version"; it is safe by construction (created only by the server, ignored by old binaries) and recorded here so it is not a precedent. An older binary's `vacuum --compact` drops it; the restart refusal on a non-empty store without a marker is the guard.

## Honest numbers

- [M] Spike, Unix socket, 2026-09-20: 0.003 ms per empty request; about 4 µs per KB of answer; unchanged from 241 k to 9.9 M tokens.
- [E] gRPC over loopback TCP adds HTTP/2 framing and protobuf encode/decode; expected well under 1 ms per request on the spike's machine (Core Ultra 9 275HX, NVMe, Linux). Stage A measures it on the same class of machine against the 5 ms trigger.
- [E] Replication cost per entry: one log fsync per node plus one apply transaction per node, plus 8 MiB of source bytes per entry across the wire. Stage B records bytes per entry, fsync throughput and replicated versus embedded ingest in `docs/spikes/raft-replication.md`.
- Effort: 37 story points over stages A-F (epic stories 20-25), plus the 2 points of this document (not counted in the epic total of 126).

The list below is by stage.

- **Every PR:** `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`, `scripts/test_gate.py`, `scripts/check-no-c-deps.py` with the deny-list, the proto regen diff job.
- **A:** proptest round-trips for every converted type and `StoreError <-> Status`; prost decode of arbitrary bytes never panics; `crates/graph-client/tests/conformance.rs` will run `run_all` with `Harness { exclusive: false }` over an in-process `TestServer` (the harness calls `open` per case with that case's extractors, so the server is (re)configured per `open` call; with `exclusive: false` the harness `locking` case returns early, so lock coverage comes from the e2e "two `serve` on one file" case below); `run_differential(&embedded, &remote)` and `run_crash_rerun_differential(&embedded, &remote)` as they exist today (the poison file is applied server-side), plus a new `server_restart_mid_batch_equals_fresh` test that restarts the server between the failing batch and the re-run; e2e spawning `memory-graph serve` and diffing `index`/`search`/`describe`/`export --server` against an embedded run on `testdata/corpus`; ADR 0003 12a acceptance (a second process reads during an index run; two `serve` on one file -> `Locked`; unknown `protocol_version` refused; the locked message names `serve` and the holder); target-selection errors and exit codes; a served file reopened embedded answers identically; RPC-overhead benchmark against the 5 ms trigger.
- **B:** `ClusterTestbed` with three nodes on `127.0.0.1:0`: bootstrap, add learners, promote, write via the leader, `wait_applied` on all, `run_differential(remote n1, remote n3)` and against the embedded oracle; leader shutdown -> election -> writes resume while reads on every node succeed throughout; a laggard behind the purge point catches up via `InstallSnapshot`; restart from persisted state; `crash_after_log_before_apply_replays_once`; `kill_during_apply_reapplies_exactly_once`; size gate adds log bytes <= 1.5x source after a corpus index plus snapshot.
