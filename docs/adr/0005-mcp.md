# ADR 0005: MCP access to the memory graph

**Status:** Accepted (2026-09-29, by the owner). The owner's decisions of 2026-09-29 on scope, transports, `rmcp` and write tools are recorded below. Follows [ADR 0003](0003-data-model.md) Q5 ("`serve` is also the MCP server") and [ADR 0004](0004-client-server-and-replication.md), which deferred MCP as issue #109 until after stage A. Epic amendment: stories 31-34 in the [epic](../epic-code-memory-graph.md).

## In plain words

1. AI assistants talk to tools through the Model Context Protocol (MCP). This ADR lets them search the graph, find symbols, describe repos and outline files.
2. There are two ways in, both read-only in v1:
   - **stdio:** the assistant starts `memory-graph mcp` itself. No network is involved. This is the default and the recommended way.
   - **HTTP:** an opt-in endpoint inside `memory-graph serve` (`--mcp-listen`). Because there is no authentication yet (#105 is deferred), it is off by default, loopback only, read-only, and protected by Origin and Host checks.
3. Tools that write (index a path, prune) are designed here but deferred until authentication exists (#105).
4. No MCP SDK is used at run time. The protocol code is hand-written, so the pure-Rust gate stays clean. `rmcp` may be a dev-dependency for tests, and only if it passes `scripts/check-no-c-deps.py`.

## Owner decisions (2026-09-29)

- v1 has two transports, both read-only: stdio (`memory-graph mcp`) and HTTP (opt-in `serve --mcp-listen`, with the D4 guards).
- Write tools (story 33) are deferred until auth (#105).
- `rmcp` may be a dev-dependency only, and only if it passes `scripts/check-no-c-deps.py`. Otherwise the real-client test uses our own client plus a recorded MCP Inspector transcript.
- The questions on scope, stdio versus HTTP, `rmcp` and write tools are resolved by the above. The questions on paging across snapshot handles, a source-excerpt tool, and the protocol revision and ports stay open (see Open questions).

## Context

- ADR 0003 Q5 named `serve` as "also the MCP server". ADR 0004 deferred it as #109 until after stage A; stages A-F have since landed.
- `serve` owns the store behind a `StoreSlot` and replicates it with Raft:
  - reads are `LOCAL` or `LINEARIZABLE` (ADR 0004 D8);
  - writes go through Raft or are forwarded to the leader;
  - `ReadMeta` travels in the `mg-read-meta` header.
- Constraints:
  - pure Rust (the gate: no `ring`, `aws-lc` or `openssl`);
  - language-agnostic;
  - works embedded (`--db`) and against a cluster;
  - `RemoteStore` panics inside a tokio runtime, so it cannot be used inside `serve`.

## Decisions

| # | Question | What was decided |
|---|---|---|
| D1 | How is MCP structured? | One tool core in a new `graph-mcp` crate, two transports: stdio (`memory-graph mcp`) and streamable HTTP inside `serve`. Hand-rolled, no SDK at run time. |
| D2 | Which tools? | Seven read-only tools: `describe`, `list_repos`, `search`, `find_symbols`, `file_outline`, `file_tokens`, `list_files`. Addressed by names, never NodeIds. |
| D3 | What backs the tools? | Embedded `open_store`, `RemoteStore`, or (inside `serve`) the existing tonic services called in-process. |
| D4 | How is an unauthenticated endpoint made safe enough? | Off by default, loopback only, Origin/Host checks, read-only, hard limits, no TLS, a boxed warning. |
| D5 | What does the CLI look like? | `memory-graph mcp` and `serve --mcp-listen ...`, with matching TOML keys, `health` and metrics. |

### D1. One tool core, two transports

- A new crate, `graph-mcp`, holds:
  - JSON-RPC 2.0 framing;
  - the MCP lifecycle: `initialize`, `notifications/initialized`, `ping`, `tools/list`, `tools/call`, cancellation;
  - the tool definitions, over a trait `McpBackend { read(ToolCall) -> Result<Value> }`.
  - It depends on graph-store types and `serde_json`, not on redb, tonic or any language crate.
- **stdio (`memory-graph mcp`)** is the default and the recommended way in.
  - It uses the same target resolution as every command: `--db`, `--server` or `MEMORY_GRAPH_SERVER`, and `--read`. It works through `open_store` or `RemoteStore`.
  - The stdio loop is synchronous, so the `RemoteStore` runtime panic cannot happen.
  - There is no socket, so no auth is needed.
  - Stdout carries only the protocol; logs go to stderr.
  - Embedded, it takes the file lock like any command. A `Locked` error names `serve`, so the user switches to `--server`.
- **Streamable HTTP inside `serve`** (`--mcp-listen <addr>`) is off unless the flag is given.
  - One POST/GET `/mcp` endpoint on a port separate from gRPC, served by axum. axum is already in the tree through tonic; verify with `cargo tree -i axum`.
  - The port is separate because the gRPC port must reach peers across the cluster, while MCP defaults to loopback.
  - v1 has no SSE resumability and no server-initiated requests. `Mcp-Session-Id` is issued and checked; the session holds only the negotiated protocol version.
- **Protocol version:** negotiated in `initialize`.
  - Support the latest stable MCP spec revision at build time and the one before it.
  - Refuse others with the spec's error.
  - Tools declare `inputSchema` and `outputSchema`, and return `structuredContent` plus a text copy.
- **Library:** hand-rolled, with no MCP SDK at run time. The `rmcp` HTTP client features pull in `reqwest`, whose default TLS would fail the gate. `rmcp` is allowed as a dev-dependency only, and only if it passes the gate.

### D2. Tools, all read-only

Shared rules:
- Every list tool takes `limit` (default 50, maximum 500; more is invalid params) and `offset`, and returns `{items, next_offset|null, stale_possible}`.
- `stale_possible` comes from `ReadMeta` and is always false when embedded.
- Tools address things by org/repo/path names, never NodeIds (ids are unstable, ADR 0003 Q1).
- Every tool carries `readOnlyHint: true`.

| Tool | Maps to | Input |
|---|---|---|
| `describe` | `StoreRead::describe` | `{org?, repo?}` |
| `list_repos` | roots + children | `{org?}` |
| `search` | `StoreRead::search(Query)` | `{text, grain: token\|symbol\|method\|class\|file\|repo\|org (default symbol), language?, org?, repo?, token_class?, symbol_kind?, limit?, offset?}` |
| `find_symbols` | `search_symbols(SymbolQuery)` | `{pattern, kind?, language?, org?, repo?, file?, limit?, offset?}` |
| `file_outline` | `search_symbols` for one file | `{org, repo, path}`; returns symbols in span order |
| `file_tokens` | `file_tokens` | `{org, repo, path, start_line?, end_line?, limit?, offset?}` |
| `list_files` | `children` / `children_page` under a repo | `{org, repo, prefix?, limit?, offset?}` |

- A hit has the fields `{grain, org, repo?, file?, language?, symbol?, symbol_kind?, lang_kind?, token_class?, span?, count, no_symbols, no_matching_symbol}`.
- A span is `{start, end, start_line, start_col, end_line, end_col}`, the same as the CLI's `--json`.
- An unknown language, kind or grain is rejected with the valid values listed.
- A paged request (`offset > 0`) runs against a fresh view in v1.
- `StoreRead::file_tokens` returns the whole file and `search_symbols` is unpaged, so in v1 the `file_tokens` line range, the 20k-token cap and all paging are applied by `graph-mcp` after loading. There is no store-side range query.
- Not exposed: vacuum, compact, membership, snapshot RPCs, export, and anything taking a NodeId.
- Errors:
  - a `StoreError` becomes a tool result with `isError: true` and a typed `{code, message}` (codes as in `graph-proto` `error.rs`); `NoLeader` is retryable;
  - JSON-RPC and protocol problems are JSON-RPC errors.
- Write tools (`index_path`, `prune`) are designed but **deferred to story 33** (until #105):
  - hidden unless `--mcp-allow-writes`;
  - confined by `--mcp-index-root`, checked after canonicalisation;
  - `prune` defaults to `dry_run`.

### D3. Backends

- Embedded: `open_store` with the shipped extractors.
- Client: `RemoteStore`, with its endpoint rotation, `--read` and deadlines.
- Inside `serve`, the `/mcp` handler calls the existing Store/Write tonic service implementations in-process, by building `tonic::Request`s. This gives the same `StoreSlot` access, linearizable barrier, `ReadMeta` and snapshot-install `UNAVAILABLE` handling as a gRPC client.
- v1 is read-only, so the adapter calls only the Store service plus the `Admin.ReadIndex` barrier for linearizable reads; the Write service is for the deferred story 33.
- Blocking calls stay on `spawn_blocking`.
- `--mcp-read local|linearizable` (default `local`). A follower serves `LOCAL` reads from its own replica.

### D4. Security defaults without auth

1. Off by default.
2. Loopback only. A non-loopback `--mcp-listen` address is refused unless `--mcp-allow-remote` is given, which also logs a warning at every start.
3. Origin and Host checks against DNS rebinding:
   - an `Origin` not in `--mcp-allow-origin` (default empty) gets 403;
   - a `Host` that is not the bound loopback name or address gets 403.
4. Read-only in v1.
5. Limits:
   - request body at most 1 MiB (413 above);
   - result at most 4 MiB, truncated with `next_offset`;
   - at most 16 requests in flight (`--mcp-max-inflight`);
   - a 30 s per-call deadline;
   - maximum `limit` 500;
   - a `file_tokens` slice of at most 20k tokens.
6. No TLS, the same stance as ADR 0004: use a sidecar.
7. A boxed warning in `docs/mcp.md` and `serve --help`: "The MCP endpoint has no authentication. Anyone who can reach it can read every indexed source token. Keep it on loopback or behind an authenticating proxy until #105."

### D5. CLI

- `memory-graph mcp [--db F | --server A,B] [--read local|linearizable]`
- `serve ... --mcp-listen 127.0.0.1:7071 [--mcp-allow-remote] [--mcp-allow-origin URL]... [--mcp-read local|linearizable] [--mcp-max-inflight N]`
- The TOML `--config` keys have the same names (`serve_config.rs`).
- `health` reports whether MCP is enabled and its address.
- Metrics gain per-tool call and error counters.

## Alternatives rejected

- A separate MCP process for HTTP, apart from `serve`: an extra hop and a second daemon (kept for stdio, where it costs nothing).
- MCP on the gRPC port: conflicts with the loopback default.
- `rmcp` at run time: a fast-moving SDK and a gate risk.
- The legacy HTTP+SSE transport: deprecated by the spec.
- NodeId navigation: ids are unstable.
- Auth first: deferred by the owner; D4 mitigates.

## Consequences

- A new public, versioned tool surface. Adding a tool or an optional field is additive; a rename or removal needs an ADR amendment.
- MCP results equal the CLI's `--json` for the same query, tested differentially, so configuration equivalence carries over.
- Someone could enable `--mcp-allow-remote` without a proxy. This is mitigated (flag, warning, docs), not prevented.
- Wire changes: `health` showing MCP (enabled, address) needs additive fields in `HelloResponse` / the health output, regenerated with the xtask (`cargo run --manifest-path xtask/Cargo.toml -- proto`). All are additive; `PROTOCOL_VERSION` stays unchanged unless a message's meaning changes.

## Test plan

1. **Tool conformance:** the same calls against three backends must equal the `StoreRead` output converted to JSON:
   - embedded `V2Store`;
   - `RemoteStore` over `TestServer`;
   - the in-serve adapter over a 3-node `ClusterTestbed`.
   Cases cover every tool, grain, filter, paging edge, unknown-value rejection, and `NoLeader` on a minority with linearizable reads.
2. **Protocol:** framing (batch rejection, ids, notifications, malformed JSON, unknown method); `initialize` version negotiation; schemas validated, and `outputSchema` checked against every `structuredContent`; a proptest over the request bytes.
3. **Security:** a non-loopback bind is refused without the flag; a foreign Origin or wrong Host gets 403; an oversize body gets 413.
4. **E2E** with the real binary over stdio and HTTP (`127.0.0.1:0`): initialize, initialized, `tools/list`, `tools/call search` on the corpus, with exact spans. The client is `rmcp` (dev-dependency, if it passes the gate) or our own client plus an Inspector transcript.
5. **Cluster e2e:** MCP on a follower returns replicated data, and reads survive a leader kill with `stale_possible: true`.
6. `cargo mutants` over the limit and guard code.
